# AI Ticket Assistant API

[![CI](https://github.com/Unequal1213/ai-ticket-assistant-api/actions/workflows/ci.yml/badge.svg)](https://github.com/Unequal1213/ai-ticket-assistant-api/actions/workflows/ci.yml)

AI Ticket Assistant API is a portfolio-ready FastAPI backend for creating,
managing, and analyzing support tickets. It demonstrates production-style API
design, SQLAlchemy database modeling, Alembic migrations, Docker-based local
development, automated tests, Ruff linting, and GitHub Actions CI.

The AI-style analysis is intentionally deterministic and local. It does not use
OpenAI or any external API, so the project can be tested and reviewed without
API keys or network-dependent AI services.

## Features

- Health check endpoint for service monitoring.
- Full Ticket CRUD API.
- Pagination, filtering, and sorting for ticket lists.
- Deterministic local ticket analysis for category, priority, summary, and suggested reply.
- PostgreSQL database foundation with SQLAlchemy ORM.
- Alembic migrations for database schema management.
- Docker Compose setup with FastAPI and PostgreSQL.
- Pytest test suite that does not require a real PostgreSQL database.
- Ruff linting.
- GitHub Actions CI for every push and pull request.

## Environment Variables

Create a local `.env` file from the example file:

```bash
cp .env.example .env
```

The example file contains placeholder values only:

```env
POSTGRES_USER=ticket_user
POSTGRES_PASSWORD=ticket_password_placeholder
POSTGRES_DB=ticket_db
DATABASE_URL=postgresql+psycopg://ticket_user:ticket_password_placeholder@postgres:5432/ticket_db
```

Do not commit real secrets. For non-Docker local development, update
`DATABASE_URL` so it points to your own PostgreSQL host, port, username,
password, and database name.

## Docker Setup

Docker Compose is the easiest way to run the full project locally because it
starts both the API and PostgreSQL.

```bash
cp .env.example .env
docker compose up --build
```

The API will be available at:

```text
http://localhost:8000
```

On startup, the app service waits for PostgreSQL to become healthy, runs:

```bash
python -m alembic upgrade head
```

and then starts Uvicorn on `0.0.0.0:8000`.

## Local Development Setup

Use these steps if you want to run the app directly on your machine instead of
inside Docker.

1. Create and activate a virtual environment:

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   ```

2. Install development dependencies:

   ```bash
   python -m pip install --upgrade pip
   python -m pip install -r requirements-dev.txt
   ```

3. Create a `.env` file:

   ```bash
   cp .env.example .env
   ```

4. Update `DATABASE_URL` in `.env` for your local PostgreSQL database.

5. Apply database migrations:

   ```bash
   python -m alembic upgrade head
   ```

6. Start the API:

   ```bash
   python -m uvicorn app.main:app --reload
   ```

## Database Migrations

Apply all migrations:

```bash
python -m alembic upgrade head
```

Create a new autogenerated migration after changing SQLAlchemy models:

```bash
python -m alembic revision --autogenerate -m "describe change"
```

Check current migration status:

```bash
python -m alembic current
```

they do not require a real PostgreSQL server.

## API Endpoints

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/health` | Returns service health status. |
| `POST` | `/tickets` | Creates a ticket from `title` and `description`. |
| `GET` | `/tickets` | Lists tickets with pagination, filtering, and sorting. |
| `GET` | `/tickets/{ticket_id}` | Returns one ticket or `404` if missing. |
| `PATCH` | `/tickets/{ticket_id}` | Partially updates a ticket. |
| `DELETE` | `/tickets/{ticket_id}` | Deletes a ticket and returns `204 No Content`. |
| `POST` | `/tickets/{ticket_id}/analyze` | Applies deterministic local analysis to a ticket. |

### Ticket List Query Parameters

`GET /tickets` supports:

- `limit`: default `20`, minimum `1`, maximum `100`
- `offset`: default `0`, minimum `0`
- `status`: optional status filter
- `category`: optional category filter
- `priority`: optional priority filter
- `sort_by`: one of `created_at`, `updated_at`, `title`, `status`, `category`, `priority`
- `sort_order`: `asc` or `desc`

Default sorting is `created_at desc`.

## Deterministic AI Analysis

The analysis endpoint uses local rule-based logic in
`app/services/ticket_analyzer.py`. It accepts a ticket title and description,
then returns:

- `category`
- `priority`
- `summary`
- `suggested_reply`

Category examples:

- `login`, `password`, `account`, `auth` -> `authentication`
- `payment`, `invoice`, `billing` -> `billing`
- `bug`, `error`, `crash`, `fail` -> `technical`
- `refund`, `cancel` -> `customer_request`
- no match -> `general`

Priority examples:

- `urgent`, `down`, `outage`, `critical` -> `high`
- `please`, `help`, `problem`, `error` -> `medium`
- no match -> `low`

This keeps the first version stable, testable, and free from external AI API
keys. A real LLM provider can be added later behind the same service boundary.

## Continuous Integration

GitHub Actions runs on every `push` and `pull_request`.

The CI workflow:

1. Checks out the repository.
2. Sets up Python 3.13.
3. Installs `requirements-dev.txt`.
4. Runs Ruff:

   ```bash
   python -m ruff check .
   ```

5. Runs Pytest:

   ```bash
   python -m pytest
   ```

The badge at the top of this README shows the current CI status.
